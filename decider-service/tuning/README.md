# Дообучение decider на сценах Готики

Strands Decider v1-2610 дообучаем на ответах `gpt-6.1-sol` по сценам из жизни NPC Хориниса. Цель — чтобы маленькая модель на 3090 решала так же, как большая, особенно там, где она проваливалась: угрозы, преступления и моменты, когда лучше ничего не делать.

## Как устроено

1. **Сцены** — [gen_cards.py](gen_cards.py). `gpt-6.1-sol` пишет «карточки»:
   - кто NPC (гильдия, характер, желание, что помнит о герое), время, расстояние;
   - что сделал герой — события тех же видов, что шлёт мост;
   - сцена текстом и меню из 4–7 вариантов. В меню есть родные озвученные SVM-реплики из `OU.BIN`.

   NPC из тестового набора ([evals/npc-decisions](../../evals/npc-decisions/README.md)) в карточках не бывает, так что тест остаётся честным. 40% запросов — о тихих моментах: герой проходит мимо, садится рядом. Иначе модель учится всегда реагировать.
2. **Вопросы** — [build_rows.py](build_rows.py). Из каждой карточки получаются два вопроса:
   - `prod`: состояние и меню ровно как их строит планировщик (`SituationBuilder`), плюс `attitude`;
   - `rich`: текст сцены и своё меню NPC с SVM-репликами — так будут выглядеть меню под тип NPC.
3. **Разметка** — [label.py](label.py), вслепую, тем же промптом, что эталонный прогон `gpt-6.1-sol` в eval. Два прохода: второй с вариантами в обратном порядке. Если проходы разошлись, ответ выбрасывается ([make_train.py](make_train.py)). Каждая десятая карточка уходит в проверку целиком.
4. **Повтор** — [make_replay.py](make_replay.py). Берём 1000 общих задач из открытого `tasksource/tasksource-jev-typed-decisions` (только строки, разрешённые для коммерческого использования). При обучении модель тянут к ответам самой v1-2610 на них, чтобы она не забыла остальное. Ещё 500 задач из других источников отложены, по ним видно, что потеряно.
5. **Обучение** — [finetune.py](finetune.py), на GPU-сервере в venv decider-сервиса. Дообучаются LoRA и голова самой v1-2610, а не новые. После обучения температуры заново подгоняются на проверочных сценах. Нужно ~6,5 ГБ видеопамяти, пилот учится 6 минут.
6. **Проверка**:
   - [score_val.py](score_val.py) — отложенные карточки;
   - `evals/npc-decisions/run_decider.py <имя> <путь к чекпоинту>` — тестовый набор из 76 сцен.

```bash
cd decider-service/tuning
uv run --project ../../server python gen_cards.py --calls 40 --quiet 0.4
uv run --project ../../server python build_rows.py
uv run --project ../../server python label.py A && uv run --project ../../server python label.py B
uv run --project ../../server python disputes.py export   # споры проходов -> судье (Claude), вслепую
uv run --project ../../server python disputes.py collect  # его ответы -> data/labels_C.jsonl
python3 make_train.py --judge C --out train_c
uv run make_replay.py --rows 1000      # нужен data/replay/validation.parquet, см. файл
rsync -a --exclude '*.parquet' ./ <gpu-host>:gothic-ai/tuning/
# на GPU-сервере, decider-сервис на это время лучше остановить:
cd ~/gothic-ai/tuning && ~/gothic-ai/decider/.venv/bin/python finetune.py --data data --train train_c --out ckpt/g7 --epochs 2
```

Данные (`data/`) в git не попадают: в них текст реплик из игры.

## Когда звать большую модель: `escalate` (2026-10-11)

Новый вопрос на прод-вопросах (`SituationBuilder.escalate`): шкала 0–4, насколько момент требует, чтобы NPC заговорил своими словами и продумал дальнейшее. Видимость для героя и бюджет — правила планировщика, не модели.

**Данные:**
- к 392 карточкам добавлены 150 «происшествий» (`gen_cards.py --emergency`): монстр бежит или нападает, драка рядом, кто-то зовёт на помощь. [build_rows.py](build_rows.py) превращает их в события протокола v6, которые шлёт мост: `monster_near`, `npc_attack`. Для `fight_nearby` и `cry_for_help` заведены новые события, мост их пока не шлёт. g5 учили на прежних формулировках этих событий («A wolf is coming at you»), сцены собраны до перехода на v6;
- два прохода по `escalate` совпали точно в 78% и в пределах одного уровня в 98%;
- **g3** — 2 эпохи от v1-2610 на всём: 1599 примеров, проверка на 186.

**Отложенные карточки** (ответы `gpt-6.1-sol`):

| модель | escalate точно / ±1 | AUROC «≥3» | react прод, с порогами | своё меню | attitude |
|---|---|---|---|---|---|
| v1-2610 | 40% / 81% | 0,86 | 15% | 47% | 65% |
| g2 | 44% / 88% | 0,90 | 67% | 53% | 91% |
| **g3** | **70% / 98%** | **0,94** | **76%** | **60%** | 89% |

**Тестовый набор, 76 сцен, ручная разметка:**

| модель | react ✓ en / ru / en_rev | ≥0,5: итог | ≥0,7: охват / верно | attitude | extra | escalate против `think` (AUROC) |
|---|---|---|---|---|---|---|
| g2 | 95 / 93 / 96% | 88% | 76% / 100% | 82% | 5/6 | 0,74 |
| g3 | 93 / 93 / 92% | 86% | 82% / 97% | 86% | 6/6 | 0,65 |

v1-2610 по тому же замеру `escalate` против `think` даёт 0,76.

**Против ручной разметки `think` хуже, и причин две:**
- **Это разные вопросы.** `think` в тестовом наборе — «да» почти только для личного разговора, а угрозы там «нет»: хватает стандартной реплики. `escalate` по замыслу ставит угрозы и происшествия высоко: в 3,4 у g3 оценено «у Лобарта убили овцу», в 2,7 — «у ворот появился орк». Ровно эти сцены и должны звать большую модель.
- **Настоящий пробел — личные дела NPC с героем.** Модель занижает сцены, где NPC есть что сказать герою при встрече: «вернулся друг» 0,8, «просрочен долг» 1,1, «обещанная награда» 1,6. В сгенерированных данных таких сцен мало, и шкала про них молчит.

### Вторая итерация: личные дела, ручной эталон, свободный текст

1. **Эталон.** Шкала дополнена: уровень 3 — это ещё и «личное дело к герою: новость, долг, обещание, обида, благодарность». По ней я вручную разметил 76 тестовых сцен ([escalate_gold.yaml](../../evals/npc-decisions/escalate_gold.yaml)) до просмотра новых ответов моделей.
2. **Данные:**
   - 77 карточек «у NPC личное дело к герою» (`gen_cards.py --personal`);
   - `escalate` переразмечен по новой шкале на всех 619 карточках;
   - после g4 `escalate` добавлен и к сценам свободным текстом (`rich`): g4 учила его только на структурированных прод-строках и на тексте сортировала хуже.
3. **g5** — 2 эпохи на всём: 2284 примера.

**Тест, 76 сцен, мой эталон `escalate`:**

| модель | уровень допустим | ±1 | AUROC «звать» (≥3) | лучший порог: верно «звать / не звать» |
|---|---|---|---|---|
| v1-2610 (не учили) | 61% | 80% | **0,86** | **82%** |
| g4 (только прод-строки) | 82% | 88% | 0,76 | 72% |
| **g5** | **86%** | **97%** | 0,79 | 76% |
| `gpt-6.1-sol` | 92% | 95% | 0,88 | 84% |

Мой эталон и `gpt-6.1-sol` сходятся в «звать / не звать» в 64 сценах из 76 (84%). Это потолок: вопрос субъективный.

- **Где g5 расходится со мной — там же, где GPT.** Открытые угрозы (кража, оружие, «бандит узнал героя») GPT и g5 ставят на 3–4, я на 2. Относительно самого GPT на этих сценах g5 сортирует с AUROC 0,88.
- **Свои промахи g5.** Занижает «ночью в спальне незнакомец», «самозванец в доспехах паладина», «вернулся друг». Завышает «Горн видит, что на друга напали».
- **Исходная модель** с хорошо сформулированной шкалой сортирует уже неплохо. Разница с g5 (0,86 против 0,79) — около полутора стандартных ошибок при 76 сценах, вывод о ней ненадёжен.
- **Дообучение** сильно подтягивает сами уровни: ±1 с 80% до 97%. Значит, фиксированный порог «уровень ≥3» у g5 означает одно и то же в разных сценах.

**Реакция у g5 — лучшая из всех:**
- `react` ✓ en / ru / en_rev — 97 / 95 / 97%;
- при пороге 0,5 охват / верно / итог — 89 / 99 / 89%;
- `attitude` 87%, `extra` 5/6;
- общие задачи 69,8% против 68,4% у v1-2610.

**Вывод.** Вопросу «звать ли большую модель» модель учится, но потолок ставит субъективность, а не модель. Для игры это работает так: g5 даёт уровень, планировщик зовёт большую модель при уровне ≥3 и только по правилам — в поле зрения героя, с бюджетом и кулдауном. Порог проще подстроить на плейтесте, чем дальше учить модель.

## Угрозы в игровом формате, разбор споров, короткие вопросы: g6, g6c, g7 (2026-10-12)

**Зачем.** g5 в игре почти не звала большую модель. На сцене «волк идёт на пастуха Малета» она давала `escalate` 1,3–1,5, а `gpt-6.1-sol` на том же состоянии — 4. Причина не в шкале, а в том, что сцены в игре выглядят иначе, чем в обучении:
- у NPC в игре нет описания характера;
- имя монстра русское («Волк is coming at you»);
- с M5c в меню есть «бежать» и «драться»;
- события `monster_killed` в обучении не было вовсе;
- Малет в игре — поселенец (GIL_OUT), а в данных поселенцев почти нет.

**Данные:**
- 200 новых карточек: 120 «спасение» (`gen_cards.py --rescue`: монстр шёл на NPC или напал, потом его убил герой, другой или сам NPC) и 80 «опасность» (`--danger`).
- У новых карточек есть вариант `game`: состояние ровно как шлёт игра, без характера, с русскими именами из скриптов игры. Для простолюдинов, горожан и крестьян добавлен ещё вариант `game_out` — тот же NPC, но поселенец.
- Строки про угрозы, у которых изменилось меню (`build_rows.py --since`), переразмечены: только `react`, 102 строки.

**Разбор споров (g6c).** Когда два прохода GPT расходятся, строка раньше выбрасывалась. Теперь третий судья (Claude, вслепую, тем же промптом, [disputes.py](disputes.py)) разрешает спор, но только если встаёт на сторону одного из проходов, и только для обучения: проверочный набор у всех вариантов один и тот же.
- Разобрано 793 строки; в обучение вернулось 690 ответов, это +20%.
- Судья встал на сторону одного из проходов: в `attitude` — всегда, в `react` — в 85%, в `escalate` — в 80%. В остальных случаях `escalate` судья обычно ставил ниже обоих проходов.

**Короткие вопросы (g7).** Формулировки `react`, `attitude` и `escalate` в планировщике сокращены, смысл и ответы разметки те же:

| запрос | было | стало |
|---|---|---|
| `react` (срочный) | 201 токен, 23,4 мс | 184 токена, 22,6 мс (−3%) |
| `attitude` + `escalate` (фоновый) | 467 токенов, 41,6 мс | 384 токена, 34,5 мс (−17%) |

Планировщик теперь задаёт `attitude` и `escalate` одним фоновым запросом (раньше двумя), так что фон после угрозы стоит примерно на 28% меньше. Общий префикс для вопросов одного запроса (strands `_slot_probs_shared_prefix`) проверен и не взят: на коротких состояниях он медленнее, 61 мс против 43 мс на запрос из трёх вопросов.

**Результаты:**

| | g5 | g6 (GPT) | g6c (GPT + судья) | g7 (g6c + поселенцы, короткие вопросы) |
|---|---|---|---|---|
| отложенные карточки: `escalate` точно / ±1 | 58% / 94% | 70% / 95% | 71% / 95% | 72% / 94%* |
| отложенные: реакция, прод-меню | 69% | 71% | 73% | 77%* |

| игровые сцены: реакция | 60% | 76% | 76% | 71%* |
| тестовый набор, 76 сцен: реакция en / итог при 0,5 | 97% / 89% | 93% / 84% | 96% / 93% | 96% / 86% |
| общие задачи (500 отложенных) | 69,8% | 69,2% | 69,4% | 68,8% |

\* В новых, коротких формулировках, на которых g7 учили. Игровые сцены у g7 — с Малетом-поселенцем ([make_probes.py](make_probes.py) `--out data/probes_g7`). Тестовый набор задаёт вопросы в своих, длинных формулировках, поэтому g7 там слегка проседает в итоге и в отношении.

**Порог `escalate`.** Планировщик сравнивает с порогом средний уровень, а средний уровень не доходит до 3, даже когда эталон говорит «звать». При пороге 3 модели зовут большую модель в 3–4 раза реже нужного, точность 64–70%. При пороге 2,5 точность 85–89%, а число вызовов близко к эталону. Порог в планировщике снижен до 2,5.

**В игре** (`SCENARIO=rescue`, Малет на ферме Лобарта):
- **g5:** убегает, молча.
- **g6c:** тоже убегает, `escalate` 2,1: Малет-поселенец для неё незнаком.
- **g7:**
  - «звать на помощь» через 31 мс, `escalate` 3,8;
  - через 6,2 с большая модель кричит на ходу: «На помощь! Волк! Не дай ему добраться до меня — я с ним не справлюсь!» — и ставит намерение «искать помощи у героя»;
  - волка Малет убил сам (скрипты отбились), и g7 героя не благодарит: `escalate` 1,7, отношение «не изменилось».

Модель g7 нельзя ставить в сервис без нового кода планировщика: она учена на коротких формулировках из `server/src/gothic_ai/brain/situation.py`. Этот код в `main` с коммита «M5c: the end of a threat; a free npc's words and body agree». И наоборот: g5 с новым кодом получает непривычные вопросы, так что сервер и сервис меняются вместе.

На игре g7 с этим кодом проходит `rescue` и `rescue_self` 8 из 8 (см. [docs/npc-agent.md](../../docs/npc-agent.md)).

## Первый звук NPC на фразу героя: вопрос `voice`, g8 и g8b (2026-10-13)

**Зачем.** Пока большая модель думает над ответом, NPC сразу издаёт звук: «Хм...», «Вот как.», «Что?!», «Тьфу!», «Ой ли?». Тип звука выбирает decider, вопрос `voice` в [reflex.py](../../server/src/gothic_ai/brain/reflex.py). На тесте [evals/talk-reactions](../../evals/talk-reactions/README.md) g7 угадывала 76%. Хуже всего — тревожные новости (`surprise` 2/9, уходят в «обычное сообщение») и оскорбления (`displeasure` 5/10).

**Данные.** Вызовов подписки нет.
- [voice_phrases.yaml](voice_phrases.yaml): 844 фразы героя по шести типам, от 107 до 163 на тип. Писал и размечал я (Claude) по тем же правилам, что тест.
- Тестовых фраз здесь нет, их близких пересказов и тех же событий тоже. Тестовых NPC (Ксардас, Лобарт, стражники у ворот) в данных нет.
- [make_voice.py](make_voice.py) даёт каждую фразу случайным NPC из карточек персонажей ([characters.json](../../server/src/gothic_ai/gamedata/characters.json)). Состояние строит код сервера (`Reflexes._state`), как в игре:
  - строка характера из карточки, у 10% её нет;
  - время и расстояние;
  - иногда место, чужак рядом и намерение NPC.
- 12% фраз записаны так, как их может дать распознавание речи: строчными, без знаков.
- Каждая десятая фраза каждого типа уходит в проверку.

**Обучение.** Данные g7 плюс строки `voice`, 2 эпохи от v1-2610.
- Сервис на это время не останавливали: в нём шла игра другой сессии. Микробатч 4 × накопление 8 — то же 32 на шаг. Обучению хватило ~6 ГБ рядом с сервисом.
- **g8** — каждая фраза двум NPC: 1516 строк, 26% игровых строк обучения. 21 минута.
- **g8b** — одному NPC: 758 строк. 19 минут.

**Звук** ([score_voice.py](score_voice.py), пороги сервера):

| | g7 | g8 | **g8b** |
|---|---|---|---|
| тест, 59 фраз: верно | 76% | 98% | **98%** |
| — `surprise` / `displeasure` | 2/9 / 5/10 | 9/9 / 9/10 | **9/9 / 9/10** |
| — сильный звук не к месту | 1 | 1 | 1 |

## Занятие на следующий час: вопрос `do`, g9–g9d (2026-10-13)

**Зачем.** Меню часа ([daylife.py](../../server/src/gothic_ai/daylife.py), шаг 6 второй волны в [npc-tools.md](../../docs/npc-tools.md#сделано-быт)) предлагает NPC сходить по заботе: рассказать новость знакомому, помолиться после увиденной смерти, запить потерю. g8b причину похода в тексте варианта не читает: на замере дня ([day_probe.py](../../evals/npc-decisions/day_probe.py)) P(chat) с новостью и без неё одинаковые, 0,29.

**Данные** — [make_day.py](make_day.py). Запросы строит код сервера (сетка замера: `daylife.day_menu`, `SituationBuilder`) для людей дампа распорядков, кроме 31 NPC замера (по id).
- Каждый NPC в два часа дня; к часу — строки без заботы и с теми заботами, для которых его меню даёт поход:
  - новость трёх видов (соврал, выманил награду, не вернул долг) о случайном знакомом;
  - тот же поход без причины (контроль);
  - смерть знакомого;
  - потеря: награда (в состоянии желание о лжи, как в игре) или долг.
- 1055 строк, 211 NPC. Разметка `gpt-6.1-sol` в два прохода, во втором меню обращены: совпало 880 (83%), 132 вызова подписки. В обучение 785, в проверку 95 (каждый десятый NPC).
- Эталон: новость — пойти рассказать 200 против 63 «как обычно»; без причины — 18 против 77; смерть — молиться 183 против 54; потеря — в таверну 68 против 125 (решает характер).

**Варианты.** Все — 2 эпохи, микробатч 4 × накопление 8, рядом с сервисом, 23–25 минут.
- **g9** — от v1-2610: данные g7 + voice1d (голос с поправкой на распознавание речи, соседняя сессия) + строки `do`;

- **g9c** — от v1-2610: данные g8b (g7 + voice1) + строки `do`;
- **g9d** — **от g8b**: учится только на строках `do`, а все строки Готики (g7 + voice1) идут повтором с ответами самой g8b как учителя, тем же механизмом, что общие задачи (`--parent ckpt/g8b`, data_g9d/replay).

## Как включить в сервисе

С 2026-10-13 сервис на GPU-сервере работает на **g9e** (дообучение от g8b, раздел о `voice` выше). До этого в тот же день — на g8b, а с 2026-10-12 — на g7.

```bash

```
