# Форк: синхронизация с автором и работа на двух ПК

Документ относится только к форку `ffring/GothicAI`.

## Как работает сейчас

**Два репозитория.**
- `ffring/GothicAI` — форк `kaifaty/GothicAI` с полным исходным кодом, единственный `origin` на Mac и на Windows. Наши правки (Windows и остальные) коммитим и пушим сюда, в `main`.
- `ffring/gothic-ai-windows` — отдельный тонкий репозиторий установщика. Он закреплён на опубликованном релизе (сейчас v0.1.1): правка `main` форка не меняет ни установленную игру, ни выпущенный ZIP.

**Синхронизация с автором** — workflow [`fork-sync.yml`](../.github/workflows/fork-sync.yml) («Fork sync») и скрипт [`scripts/fork-sync.sh`](../scripts/fork-sync.sh).
- Раз в сутки (03:17 UTC; GitHub может запустить позже) и по кнопке Run workflow вливает `main` автора в наш `main` обычным merge-коммитом и пушит без force. Наши коммиты и история остаются как есть.
- Merge делает git тем же алгоритмом, что `git merge` (`git merge-tree`), в клоне на раннере GitHub. Локальные копии на Mac и Windows бот не трогает: незакоммиченная и незапушенная работа там остаётся на месте, а её push пройдёт через обычный `git pull` (раздел «Работа на двух ПК»).
- Если наш `main` уже содержит `main` автора, бот ничего не пушит, в сводке прогона — «Up to date».
- Бот ничего не пушит, а прогон краснеет с причиной в сводке, если:
  - merge даёт конфликт — сводка перечисляет файлы;
  - автор менял файлы `.github/workflows/`: токен Actions не может их пушить, а новый workflow начнёт запускаться в форке, поэтому сначала его читает человек;
  - push отклонён, хотя `main` не двигался (правило на ветке или права токена).
- Если `main` сдвинулся во время прогона (push с другого ПК), бот повторяет merge поверх нового `main`, до трёх попыток.
- В репозиторий автора бот не пишет: `GITHUB_TOKEN` достаёт только до нашего репозитория. Другие ветки, в том числе `windows-upstream-0.1.1` (PR548 автору), он не трогает.
- Бот ничего не собирает и не тестирует. Сводка прогона показывает, какие каталоги поменял автор; по ней решают, нужна ли сборка (раздел «Исходники, сборка и релиз»). Push от `GITHUB_TOKEN` не запускает других workflow, а CI на push в форке и так нет.
- Защита от запуска не там: job идёт только в `ffring/GothicAI` и только с `main`, первый шаг сверяет через API, что форк сделан от `kaifaty/GothicAI`. Адрес автора записан в workflow и вводом не меняется. Права — только `contents: write`; секреты и PAT не нужны.

**Проверка.**
- Офлайн-тест на временных репозиториях: [`scripts/tests/test_fork_sync.py`](../scripts/tests/test_fork_sync.py), запуск — `uv run --locked --project launcher/core pytest -q scripts/tests/test_fork_sync.py`.
- На GitHub: Actions → Fork sync → Run workflow (флажок `dry_run` — только проверить) или `gh workflow run fork-sync.yml -R ffring/GothicAI` (с `-f dry_run=true` — только проверить). Без новых коммитов автора прогон зелёный, в сводке «Up to date».

**Как выключить.** `gh workflow disable fork-sync.yml -R ffring/GothicAI` или Actions → Fork sync → Disable workflow; включить — `gh workflow enable fork-sync.yml -R ffring/GothicAI`. Ручное влитие (раздел «Если бот остановился») работает и без бота. GitHub сам выключает расписание публичного репозитория после 60 дней без активности; включается той же командой.

## Работа на двух ПК

На Mac и на Windows один `origin` — `https://github.com/ffring/GothicAI.git`. В `main` пушат оба ПК и бот, поэтому:

1. **Перед работой:** `git status`. Незакоммиченную работу закоммить: merge локальный коммит не потеряет. Затем `git pull --no-rebase origin main`.
2. **После работы:** закоммить, снова `git pull --no-rebase origin main`, проверь то, что пришло (раздел «Исходники, сборка и релиз»), затем `git push origin main`. Push отклонён — снова `pull` и `push`.
3. **История только растёт.** Расхождение решай merge-коммитом. `--force` и `--force-with-lease`, `reset --hard`, rebase запушенного и удаление веток теряют работу другого ПК или незапушенную работу, поэтому их не используем.

`--no-rebase` указан явно: если в чьём-то конфиге `pull.rebase=true`, rebase переписал бы незапушенные коммиты.

В форке `main` принимает обычный push, PR не обязателен. Разделы `AGENTS.md` о Ryzen, `dev-ubuntu`, `gq` и защищённом `main` описывают машины и репозиторий автора.

Ветки PR автору (сейчас `windows-upstream-0.1.1`, PR548) режем от `main` автора. В них только сама правка, без служебных файлов форка: этого документа, `fork-sync.yml`, `fork-sync.sh`.

Кнопка Sync fork на странице форка: «Update branch» делает тот же merge, а «Discard N commits» стирает наши коммиты — её не нажимаем.

## Если бот остановился

Причина — в сводке красного прогона Fork sync. О красном прогоне по расписанию GitHub уведомляет того, кто последним менял расписание в workflow, если у него включены уведомления Actions.

Влить вручную на любом ПК, после шага 1 раздела «Работа на двух ПК»:

```sh
git remote add upstream https://github.com/kaifaty/GothicAI.git  # один раз
git fetch upstream
git merge upstream/main
# конфликт: поправь файлы, затем git add <файлы> и git commit
git push origin main
```

- **Конфликт.** Сохраняй наши правки и добавляй правки автора. Если не ясно, чья версия нужна, спроси пользователя.
- **Файлы workflow.** Прочитай новые и изменённые `.github/workflows/*` автора: после merge они запускаются в форке. Ненужный в форке workflow выключи командой `gh workflow disable <файл> -R ffring/GothicAI`, а сам файл не правь: правка конфликтовала бы при следующих синхронизациях.
- **Push отклонён.** Если `main` просто двигался, запусти Run workflow ещё раз. Если отклонён снова, проверь правила ветки `main` в настройках репозитория: бот пушит в неё напрямую.

После ручного влития следующий прогон бота — «Up to date».

## Исходники, сборка и релиз

- Синхронизация меняет только исходники в `main` форка. Установленная игра и выпущенный архив остаются прежними.
- Играбельная сборка Windows — ручной workflow «Windows release» ([`windows-release.yml`](../.github/workflows/windows-release.yml)): без флажка он собирает и проверяет, с `draft_release` ещё делает черновик пререлиза. Установщик `ffring/gothic-ai-windows` даёт игроку новую версию, только когда его закрепление переведут на новый опубликованный релиз.
- Проверочный прогон Windows release нужен перед релизом и когда меняется то, что входит в сборку: `OpenGothic/`, `scripts/convert/`, `scripts/build-engine.ps1`, `scripts/windows/`, Python-проекты `launcher/core`, `server`, `asr-service`, `tts-service`, `libs/chatgpt-auth`. Полный состав — в `windows-release.yml` и `scripts/windows/package.ps1`.
- Документы, отчёты, `research_notes/` и `site/` сборки не требуют. Зелёный прогон на том же коммите не повторяем. Если после него пришли только такие файлы, его результат остаётся в силе, хотя SHA `main` сменился.
- После merge гоняем только тесты изменённых модулей; полный `pytest` и сборка ради самой синхронизации не нужны.
