# Этап 9.3 после слияния с main: lockstep, realtime и новая native-база

17 октября 2026 года, Ryzen 9 3950X. После слияния ветки боевого тела с main (PR #153: Jolt,
физический персонаж NPC) runner собран заново и проверен тремя способами:

- 64 + 64 отложенные дуэли P30 в realtime драйвером gate;
- те же дуэли в lockstep коллектором;
- полная процедура gate.

Сила P30 в lockstep на 2048 дуэлях после слияния описана в плане (9.3).

**Итог.**

- **Lockstep принимает те же решения, что realtime.** Ни одна из 128 дуэлей не разошлась без сбоя
  realtime, исход совпал во всех 128. Оценку в lockstep по-прежнему можно переносить на realtime.
- **Сбоев realtime стало намного больше.** Шаг runner на новом движке длиннее примерно на 4,6 мс:
  медиана 25,3 мс против 20,7 мс при тике 33,3 мс, а в первую секунду боя — 29 мс. Окно, в которое
  команда успевает до следующего шага, сжалось до 2–4 мс. Поэтому 100 команд из 2361 отклонены как
  устаревшие (до слияния 1 из 2194). Тик в тик с lockstep совпали 25 из 64 открытых дуэлей и 15 из
  64 у стены (до слияния 64 и 63).
- **По процедуре gate P30 на новом движке проходит все пороги, кроме нагрузки 4 NPC.** Там доля
  нейронного управления 0,918 при пороге 0,95 (на старом движке 0,986). Причина та же: в мире с
  четырьмя управляемыми NPC команды чаще опаздывают на тик.
- **Native-база для следующего gate заведена.** Это новый эталон native-off и прогон
  `stage9-rt-eval-v5`. Native-эпизоды нового движка совпадают со старыми только в 46 из 95, так
  что старая база больше не годится.

## Lockstep против realtime

| | Открытая, до слияния | Открытая, после | У стены, до | У стены, после |
|---|---:|---:|---:|---:|
| Тик в тик | 64/64 | 25/64 | 63/64 | 15/64 |
| Разошлись после сбоя realtime | 0 | 39 | 1 | 49 |
| **Разошлись без сбоя** | **0** | **0** | **0** | **0** |
| Тот же исход | 64 | 64 | 64 | 64 |
| Отклонённые команды realtime | 0 из 1136 | 50 из 1209 | 1 из 1058 | 50 из 1152 |
| Опоздавшие команды | 0 | 8 | 0 | 5 |
| Опросы, увидевшие больше одного тика | 1 | 81 | 20 | 72 |

Каждое расхождение начинается со сбоя realtime, который lockstep воспроизвести не может:

- команда отклонена (`stale_observation`);
- команда принята на тик позже;
- опрос увидел сразу несколько тиков.

Исход дуэли от этого не меняется. Но HP в realtime теперь чуть ниже, чем в lockstep: 289,4 против
293,7 на открытой арене и 281,4 против 285,9 у стены.

## Почему realtime сбоит чаще

Драйвер gate ждёт наблюдение следующего тика, прогоняет модель и арбитраж и отправляет команду
примерно через 2,8 мс после наблюдения. Runner читает команды только между шагами. Если следующий
шаг начался раньше, чем пришла команда, она ссылается на устаревшее наблюдение. Тогда runner её
отклоняет, а драйвер решает заново по следующему наблюдению.

| P30, открытая арена | До слияния | После | После, потоки Jolt = 4 (16 дуэлей) |
|---|---:|---:|---:|
| Шаг (от срока до конца), медиана, мс: первая секунда / дальше | 24,6 / 20,7 | 29,1 / 25,3 | 28,8 / 25,0 |
| — p95, мс: первая секунда / дальше | 26,6 / 24,0 | 31,4 / 28,5 | 30,8 / 28,2 |
| Окно до следующего шага, p5, мс: первая секунда / дальше | 6,5 / 9,4 | 2,0 / 4,8 | 2,4 / 5,1 |
| — медиана, мс: первая секунда / дальше | 8,7 / 12,6 | 4,3 / 8,0 | 4,5 / 8,2 |
| Отклонённые команды | 0 | 50 из 1209 | 2 из 289 (без потоков на тех же дуэлях — 22 из 327) |

- **Сами тики остались ровными:** p99 интервала 36 мс, задержек больше 45 мс нет. Медленнее стал
  каждый шаг, а не отдельные.
- **Сбои сосредоточены в начале боя.** Из 50 отклонений на открытой арене 32 приходятся на первую
  команду эпизода, ещё 16 — на первую секунду, позже только 2. В первую секунду шаг тяжелее всего,
  и окно там в медиане 4,3 мс.
- **Потоки Jolt шаг почти не укорачивают** (−0,3 мс). Значит, лишнее время — последовательная
  работа, а не параллельный шаг физики. Отклонений в диагностике меньше, 2 против 22. Но окно
  выросло всего на 0,2–0,5 мс, так что на 16 дуэлях вывода из этого нет. К тому же потоки ломают
  fork-reset и общее расписание с lockstep.
- **Что именно стало дороже, не измерено.** Кандидаты:
  - обновления физических персонажей двух NPC — в Jolt они идут последовательно;
  - работа новых систем main на каждом шаге.

## Процедура gate на новом движке

| | P30, старый движок (v4) | P30, новый движок (v5) | Порог |
|---|---:|---:|---:|
| Обычный realtime: neural control (min) | 1,0 | 1,0 | ≥ 0,95 |
| — model step / collector → send / observation → arbitration p95, мс | 1,19 / 1,63 / 2,88 | 1,29 / 1,67 / 3,02 | 5 / 20 / 100 |
| Защитная реакция: collector → send / obs → arbitration p95, мс | 7,07 / 8,63 | 7,61 / 9,22 | ≤ 20 / ≤ 100 |
| Блок после замаха, игровые мс (окно удара) | 66 (166) | 66 (166) | в окне |
| **Нагрузка 4 NPC: neural control (min)** | 0,986 | **0,918** | ≥ 0,95 |
| — model step / collector → send / obs → arbitration p95, мс | 1,11 / 3,71 / 5,68 | 1,17 / 5,49 / 36,6 | 5 / 20 / 100 |
| — отклонённые команды за повтор | 1–2 | 9–12 | |
| Runtime fallback | 0 | 0 | 0 |
| Screening: успех против native, п.п. (дуэль) | +55 | +45 | ≥ −15 |
| Screening: дистанция / атака / блок / дуэли | 20 · 20 · 20 · 20 из 20 | 20 · 20 · 20 · 20 из 20 | |
| Screening-дуэли: HP P30 | 280,1 | 283,6 | |
| Screening-дуэли: победы native | 9/20 | 11/20 | |

- **Порог нарушен только в нагрузке.** Все четыре повтора дают 0,918–0,940. С четырьмя
  физическими NPC шаг ещё тяжелее: наблюдение → арбитраж p95 выросло с 5,7 до 36,6 мс, но до
  порога в 100 мс далеко.
- **Остальные пороги пройдены.** В фазе realtime два эпизода нейтрального блока потеряли по одной
  команде (доля 0,889 и 0,5). Блок в порог обычного realtime не входит, как и в gate v16.
- **Native стал сильнее в дуэли:** 11 побед из 20 против 9. Поэтому разница успеха P30 с native
  сократилась с +55 до +45 п.п.

## Новая native-база

**1. Эталон native-off.**

- Setup gate сравнивает свежую запись native-off с эталоном этапа 3
  (`body-headless/runs/stage3-v1/native-off`, старый движок). Native-off — три нативные дуэли
  стенда, seed 17, 29 и 43.
- На новом runner запись расходится с эталоном: длительность 14,1 / 15,6 / 23,6 с стала 21,3 /
  18,4 / 21,3 с, порядок событий другой. Поэтому setup любого gate на новом движке падал бы.
- Новый эталон — первая запись native-off на новом runner: `~/gothic-ai/body/data/native-base-v1/native-off`.
  Её сделала первая попытка setup v5; она сохранена как `setup-probe-vs-stage3`.
- Повторный setup записал native-off заново, и запись совпала с эталоном: 0 различий на 418, 365 и
  406 проверках порядка.

**2. Native-эпизоды фаз gate.**

- Прогон v5 даёт 95 native-эпизодов: shadow 1, realtime 8, реакция 2, screening 80, нагрузка 4.
- Со старым движком совпали 46 из 95: shadow 0/1, realtime 4/8, реакция 2/2, screening 40/80,
  нагрузка 0/4. На старом движке повтор gate давал 95 из 95 (v4 против gate v16).

**3. Как следующей процедуре gate использовать базу.**

```sh
GOTHIC_BODY_SSH=ryzen GOTHIC_BODY_ENGINE=gothic-ai/body-api-merged \
GOTHIC_BODY_PREPARE_CODE=gothic-ai/<замороженный код gate с новым именем прогона> \
GOTHIC_BODY_NATIVE_REFERENCE=gothic-ai/body/data/native-base-v1/native-off \
  scripts/body-bc-remote.sh prepare <run>   # затем setup, shadow, realtime, realtime-reaction, load, screening-reaction
python3 body_stage9_gate_compare.py --gate stage8-final-gate-v16 --baseline stage9-rt-eval-v5 \
  --candidate <run> --output <compare.json>
```

- **Проверка базы:** `native replay` должен показать 95 из 95. Тогда GRU-эпизоды кандидата
  сравниваются с P30 на том же движке.
- **Заморозка кода:** v5 замораживал код v4 с конфигурациями
  [`stage9-rt-eval-v5`](../../../evals/npc-body/stage9-rt-eval-v5/), копия лежит в
  `~/gothic-ai/body/rl/gate-v5-code`.
- **Новая сборка движка — новая база:** другой runner требует снова записать native-off и прогнать
  gate.
- **Повторяемость:** то, что 95 native-эпизодов фаз повторяются на новом движке, проверит первая же
  следующая процедура. Пока проверен повтор только native-off.

## Изменения в скриптах

- **[`body-bc-remote.sh`](../../../scripts/body-bc-remote.sh)** получил три переменные, значения по
  умолчанию прежние:
  - `GOTHIC_BODY_ENGINE` — папка движка (исходники, сборка и provenance);
  - `GOTHIC_BODY_PREPARE_CODE` — какой код замораживает `prepare`;
  - `GOTHIC_BODY_NATIVE_REFERENCE` — эталон native-off для setup.
- **[`body-stage9-duels.sh`](../../../scripts/body-stage9-duels.sh)** получил `DUELS_ENGINE`:
  движок, который записывается вместе с `DUELS_RUNNER`.
- **[`body_stage9_gate_compare.py`](../../../scripts/body_stage9_gate_compare.py)** получил
  `--baseline` (с каким прогоном процедуры парить кандидата) и подсчёт совпавших native-эпизодов.
  На старых данных v4 против gate v16 подсчёт даёт 95 из 95.

## Ограничения и что дальше

- **Главная находка — сбои realtime на новом движке.** Из-за них gate проваливает порог нагрузки.
  Возможно, то же самое ждёт этап 10, если сервис политики получает наблюдения тем же способом.
  Это стоит проверить нагрузочным прогоном этапа 10.
- **Порядок работы дальше:**
  1. профиль шага runner ([`body-runner-gdb-sample.sh`](../../../scripts/body-runner-gdb-sample.sh));
  2. убрать лишнюю работу;
  3. повторить realtime-дуэли и gate.

  Ослаблять порог 0,95 нельзя.
- **Lockstep тоже медленнее.** Коллектор на 64 дуэлях (16 воркеров) работал 11,7 с вместо 8,0 с.
  Перед следующими раундами RL пропускную способность стоит перемерить
  (`scripts/body_sim_bench.py`).
- Сила P30 по-прежнему видна только в lockstep на 2048 дуэлях, а в realtime — на 128 дуэлях, где
  сильные модели почти всегда выигрывают.
