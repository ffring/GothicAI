# Этап 9: лёгкий Python в сборе

15 октября 2026 года, Ryzen 9 3950X. После заморозки мира больше половины CPU сбора тратил Python.
Теперь строка упаковывается один раз, быстрым упаковщиком с побитово теми же признаками, а runtime
не считает хэши провенанса. **Эпизоды и обучающие данные не изменились. Сбор быстрее на 27–40%:**
420 решений/с на 16 воркерах (было 309), 431 на 24.

## Что было

cProfile одного воркера, 16 дуэлей: 24,1 с.

- Упаковка признаков — 9,8 с. Каждая периодическая строка упаковывалась дважды: внутри runtime и
  ещё раз коллектором для обучающих данных. Одна упаковка стоила 0,94 мс. Эталонный упаковщик
  строит набор признаков трижды за вызов (в проверке строки, при пересчёте имён и для самих
  признаков) и заново проверяет каждое значение нормализатора: 6,6 млн проверок конечности чисел.
- Хэши провенанса в runtime — около 1 с. Четыре `json.dumps` на строку и ещё два при арбитраже.
- Сама GRU — 0,23 мс на шаг.

## Как устроено

- **Один раз.** Runtime сохраняет признаки последней обработанной строки (`last_features`), и
  коллектор берёт их, а не упаковывает строку заново.
- **Быстрый упаковщик** [`scripts/body_fast_features.py`](../../../scripts/body_fast_features.py).
  Те же правила проверки и тот же порядок признаков, но набор строится один раз, а векторы
  нормализатора проверяются один раз на объект нормализатора. Каждое значение проходит те же
  операции с плавающей точкой, поэтому результат совпадает побитово. Эталонный упаковщик
  `body_trajectory_dataset.pack_features`, привязанный к gate, не менялся.
- **Лёгкий runtime** (`PolicyRuntime(lean=True)`). Отпечатки строк — кортежи (номер, источник,
  флаг памяти). При арбитраже строка сравнивается с обработанной напрямую. Хэши и проверка размера
  запроса не считаются. Решения, память и отказы те же. По умолчанию `lean=False` — прежнее
  поведение.
- **Коллектор** включает оба по умолчанию. `--reference-runtime` возвращает эталонный упаковщик
  и полный runtime.

на Python-процесс (копия torch) и 0,26 ГБ на runner.

## Что ограничивает теперь — сброс

Сброс стал больше самого боя. Бой в замороженном мире длится 0,3–0,5 с, а сброс занимает 47%
времени эпизода на одном воркере, 53% на 16 и 61% на 24. Временные замеры внутри runner
показали: из ~135 мс сброса 132 мс — первый тик сценария стенда. В нём `set time 12 0`, `goto` и
`turn`, и установка времени суток пересчитывает распорядок всех NPC Хориниса. Это повторяется в
каждом fork, хотя от конфигурации эпизода не зависит.

Следующие шаги:

1. Выполнять начало сценария (время, перемещение героя, ожидание, очистку площадки) один раз в
   шаблоне и делать fork прямо перед `bodyarena`. Ожидается сброс runner в единицы миллисекунд.
   Эквивалентность проверить тем же инструментом.
2. Один процесс-драйвер на несколько runner с пакетным инференсом — меньше копий torch.

## Ограничения

- Изменения `gothic_body/runtime.py` и новый упаковщик меняют хэши модулей. Следующему gate
  нужны новые привязки. Замороженные прогоны хранят свои копии.
- Быстрый упаковщик проверен на дуэлях и коротких задачах с родным противником.
  Строки `near_wall` и подготовленной реакции в выборку не входили.
