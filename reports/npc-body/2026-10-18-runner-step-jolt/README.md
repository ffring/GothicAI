# Этап 9.3: почему шаг runner вырос после Jolt и как вернуть окно команде

18 октября 2026 года, Ryzen 9 3950X. После слияния с main (PR #153) шаг `gothic-body-runner` в
realtime вырос примерно на 4,6 мс. Окно, за которое команда драйвера gate должна успеть до
следующего шага, сжалось до 2–4 мс, и 4% команд отклонялись как `stale_observation`
([перепроверка](../2026-10-17-merged-engine-recheck/README.md)). Здесь снят профиль шага на старом
и новом runner, найдена причина и проверена правка.

**Итог.**

- **Шаг дорожает в трёх местах, и вся работа последовательная, на потоке runner.** В профиле 16
  дуэлей прибавка — +3,6 мс CPU на шаг после первой секунды боя:
  - лучи foot IK к земле: +1,7 мс. Каждый шаг каждый NPC мира пускает лучи под ступни. Jolt
    медленнее Bullet на 0,7 мс, ещё 1,2 мс — обёртка луча из main с уточнением по исходным
    плоскостям меша;
  - поза NPC: +0,6 мс, из них 0,4 мс — новый прицел NPC (`Aim::finish`);
  - мир: +1,0 мс — шаг физики, живые тела, интерактивные и подвижные предметы.
- **Дешевле всего ускорить сам Jolt.** В нашей сборке он собран под SSE2 («portable»), и обход
  дерева в лучах идёт через программные заглушки: half → float, popcount, перестановки компонент.
  На них уходит около 2 мс шага.
- **Правка: Jolt на наборе x86-64-v3.** Это AVX2, F16C, BMI1 и LZCNT, без FMA.
  - Новая опция CMake `OPENGOTHIC_JOLT_X86`. По умолчанию прежний `portable`.
  - Сборка runner (`scripts/body-api-remote.sh`) включает `x86-64-v3`, если у хоста есть
    нужные инструкции. Ryzen и dev-ubuntu их поддерживают.
  - Код Jolt на шаг: 8,4 → 6,1 мс, быстрее Bullet до слияния (7,7). Весь шаг: 25,3 → 22,9 мс
    CPU, до слияния 21,7.
- **Механика не изменилась.** Jolt собран с `CROSS_PLATFORM_DETERMINISTIC`, и результат от набора
  инструкций не зависит. Проверено:
  - 128 из 128 lockstep-эпизодов P30 совпали с runner после слияния бит в бит, во всех четырёх
    журналах;
  - native-off совпал с эталоном native-base-v1;
  - native-эпизоды процедуры gate совпали с прогоном v5 в 95 из 95.
- **Шаг и окно вернулись почти к прежним.** На 64 + 64 отложенных дуэлях P30 в realtime:
  - окно p5 после первой секунды — 8,1 мс, было 4,8–5,1 (до слияния 9,4–10,0);
  - отклонённых команд 2 из 2188, было 100 из 2361 (до слияния 1 из 2194);
  - тик в тик с lockstep совпали 62 из 64 открытых дуэлей и 63 из 64 у стены, было 25 и 15.
- **Gate (`stage9-rt-eval-v6`): P30 на v3 проходит все пороги, включая нагрузку 4 NPC.** Доля
  нейронного управления там 0,985, порог 0,95. На v5 было 0,918, на старом движке 0,986.

## Как снят профиль

`perf` на Ryzen закрыт (`perf_event_paranoid=4`). `body-runner-gdb-sample.sh` останавливает процесс
на каждом сэмпле, и realtime-шаг под ним не измерить. Поэтому написан сэмплер по времени CPU:
[`body-runner-cpu-sample.c`](../../../scripts/body-runner-cpu-sample.c), PR #188.

- Сэмплер подключается через `LD_PRELOAD` в обёртке, которую драйвер получает как `--runner`.
- `ITIMER_PROF` срабатывает только пока процесс занимает процессор, поэтому сон между тиками в
  профиль не попадает.
- Каждый сэмпл помечен `CLOCK_MONOTONIC`. Тем же часам принадлежат срок тика
  (`next_tick_wall_monotonic_ns`) и момент семпла наблюдения.
- [`body_runner_step_profile.py`](../../../scripts/body_runner_step_profile.py) `profile` относит
  каждый сэмпл к шагу в том смысле, в каком его меряет gate: от срока тика до семпла наблюдения.
  Затем он считает мс CPU на шаг по функциям. Подкоманда `window` считает шаг, окно и отклонённые
  команды так же, как перепроверка.

Сценарий — первые 16 отложенных дуэлей P30 на открытой арене (seed 90000–90015) через
[`body-stage9-duels.sh`](../../../scripts/body-stage9-duels.sh) `realtime` в классе quiet, сэмпл
раз в 1 мс CPU. Профили сняты на трёх runner:

- **old** — до слияния: Bullet, `body-api`, `f4e12bce`;
- **new** — после слияния: Jolt на SSE2, `body-api-merged`, `aa13181f`;
- **v3** — тот же `aa13181f` с Jolt на x86-64-v3.

CPU на шаг совпадает со стеночным временем шага: 22,07 и 22,16 мс на old, 25,69 и 25,76 мс на new.
Значит, шаг ничего не ждёт, всё лишнее — работа процессора. Сэмплер почти не удлиняет шаг: медиана
после первой секунды под ним 24,9 мс против 25,3 без него.

На v3 сэмплер пишет только pc из контекста сигнала (`CPUSAMPLE_FLAT=1`). `backtrace()` из
обработчика сигнала роняет runner, собранный с AVX, поэтому для v3 есть только плоский профиль.

## Что стало дороже

Мс CPU на шаг после первой секунды боя, профиль 16 дуэлей.

| | old (Bullet) | new (Jolt, SSE2) | v3 (Jolt, x86-64-v3) |
|---|---:|---:|---:|
| **Весь шаг** | **21,7** | **25,3** | **22,9** |
| Код физики: Bullet или Jolt (по pc) | 7,7 | 8,4 | 6,1 |
| Код движка (по pc) | 12,9 | 15,2 | 15,4 |
| libc и libm (по pc) | 1,1 | 1,7 | 1,4 |

Шаг new по поддеревьям, против old:

| Где | old | new | Разница |
|---|---:|---:|---:|
| Анимация NPC (`WorldObjects::updateAnimation`) | 19,2 | 21,9 | +2,6 |
| — foot IK, лучи к земле (`FootIk::mkInput` → `DynamicWorld::ray`) | 7,2 | 8,9 | +1,7 |
| — — из них Jolt `NarrowPhaseQuery::CastRay` / Bullet `rayTest` | 7,3 | 8,0 | |
| — — обёртка луча main: уточнение по исходным плоскостям, нормаль | — | 1,2 | |
| — поза: `Pose::update` и `Pose::updateFootIk` | 9,9 | 10,5 | +0,6 |
| — — из них прицел NPC (`Aim::finish`, новое в main) | — | 0,4 | |
| Мир (`World::tick`) | 2,2 | 3,2 | +1,0 |
| — шаг физики и подвижные предметы (`DynamicWorld::tick`) | 0,04 | 0,41 | +0,4 |
| — регдоллы и живые тела (`prepareRagdolls`, новое в main) | — | 0,32 | +0,3 |
| — интерактивные предметы (`PhysicMesh::setPose`) | 0,06 | 0,25 | +0,2 |
| — NPC и прочее (`WorldObjects::tick` без предметов) | 2,1 | 2,2 | +0,1 |

**Самая крупная часть — лучи foot IK, и всё время в них последовательное.** Jolt вызывается на потоке
runner (`OPENGOTHIC_PHYSICS_THREADS=0`). Потоки Jolt распараллеливают только шаг физики, а это
0,2 мс. Поэтому `OPENGOTHIC_PHYSICS_THREADS=4` в перепроверке почти ничего не дал.

**В лучах Jolt видны заглушки SSE2.** Мс на шаг:

- `HalfFloatConversion::ToFloatFallback` — 0,84;
- `__popcountdi2` — 0,41;
- скалярный цикл `UVec4::ShiftComponents4Minus` — 0,91;
- `Vec4::sSelect` через and/andnot/or — 1,1.

Это ровно то, что Jolt делает одной инструкцией с F16C, POPCNT и SSE4.1.

OpenGothic собирал Jolt без x86-расширений ради переносимого бинарника
([`OpenGothic/CMakeLists.txt`](../../../OpenGothic/CMakeLists.txt)). В main это не заметно: игра на
Mac идёт на ARM, а там Jolt использует NEON.

**На v3 код Jolt стоит 6,1 мс на шаг**: на 2,2 мс меньше, чем на SSE2, и на 1,5 мс меньше, чем
Bullet до слияния. Оставшиеся +1,2 мс к шагу до слияния — новые системы main в коде движка. Их
эта правка не трогает: каждую пришлось бы отдельно проверять на неизменность поведения. Это:

- прицел NPC;
- уточнение лучей по исходным плоскостям меша;
- живые тела;
- шаг физики мира.

## Правка

- **[`OpenGothic/CMakeLists.txt`](../../../OpenGothic/CMakeLists.txt): опция
  `OPENGOTHIC_JOLT_X86`.**
  - `portable`, по умолчанию, оставляет прежний SSE2.
  - `x86-64-v3` включает у Jolt SSE4.1/4.2, AVX, AVX2, LZCNT, TZCNT и F16C.
  - FMA выключена всегда: `USE_FMADD` выключен, `-ffp-contract=off` остался.
  - В бинаре v3 нет ни одной FMA-инструкции (`objdump`): 14 тыс. инструкций с ymm-регистрами,
    108 `vcvtph2ps`.
- **[`scripts/body-api-remote.sh`](../../../scripts/body-api-remote.sh): сборка runner для gate и
  RL.** Это цепочка `body-bc-remote.sh build` → `body-trajectories` → `body-arena` → `body-api`.
  - Она передаёт `x86-64-v3`, если в `/proc/cpuinfo` есть `avx2`, `f16c`, `bmi1` и `abm`.
  - Иначе остаётся `portable`.
  - Ryzen 3950X и Ryzen 9955HX на dev-ubuntu эти инструкции поддерживают.
- **Игра и прочие сборки** (`build-engine.sh`, `ryzen.sh` для e2e) не тронуты.

**Почему результат не меняется.** Jolt собран с `CROSS_PLATFORM_DETERMINISTIC`. Это режим, в
котором Jolt даёт одинаковый результат на разных платформах и наборах инструкций. Например, сумма
компонент вектора там считается как `(x + y) + (z + 0)` и на SSE4.1, и на NEON, и без SIMD. Новые
инструкции заменяют лишь заглушки, которые считают то же самое: half → float, popcount, выбор по
маске, перестановки. Проверено на runner:

- **Lockstep, бит в бит.** 64 открытые дуэли и 64 у стены коллектором
  ([`body_rl_collect.py`](../../../scripts/body_rl_collect.py) `--keep-journals`) на v3.
  [`body_lockstep_journal_diff.py`](../../../scripts/body_lockstep_journal_diff.py) сравнил их с
  тем же прогоном runner после слияния, без полей времени:
  - `observations.jsonl` — 128/128;
  - `events.jsonl` — 128/128;
  - `arena-events.jsonl` — 128/128;
  - `body-control-events.jsonl` — 128/128.

  Контроль: lockstep старого движка против нового тот же скрипт различает — `observations.jsonl`
  совпали в 0 из 64.
- **Native-off против эталона native-base-v1:** `matched` (setup gate v6).
- **Native-эпизоды процедуры gate:** 95 из 95 совпали с прогоном v5
  ([`body_stage9_gate_compare.py`](../../../scripts/body_stage9_gate_compare.py) `--baseline
  stage9-rt-eval-v5`). Native-база v1 остаётся годной и для runner на x86-64-v3.

## Процедура gate на v3

Прогон `stage9-rt-eval-v6` — как `stage9-rt-eval-v5`, изменены только runner и имя прогона:

- runner — v3, `df94b627…`, через `GOTHIC_BODY_ENGINE=gothic-ai/runner-step-engine`;
- замороженный код — код v5 с [конфигурациями v6](../../../evals/npc-body/stage9-rt-eval-v6/);
- эталон native-off — `native-base-v1`;
- фазы: setup, shadow, realtime, realtime-reaction, нагрузка, screening;
- сравнение: `body_stage9_gate_compare.py --gate stage8-final-gate-v16 --baseline
  stage9-rt-eval-v5 --candidate stage9-rt-eval-v6`.

## Что дальше

- **Следующий gate на runner из main** собирается через `body-bc-remote.sh build` и сам получает
  `x86-64-v3`. Его native-эпизоды можно сравнивать с v5 или v6 (`--baseline`), пока не изменится
  код движка.
- **Оставшиеся +1,2 мс к шагу до слияния** — новые системы main. Если окна станет мало
  (например, в нагрузке этапа 10), следующие кандидаты:
  - `Aim::finish`, 0,4 мс: проверить, нужен ли он NPC без лука;
  - уточнение лучей по исходным плоскостям, 1,2 мс.
- **Сэмплер на AVX-сборке** даёт только плоский профиль. Полные стеки там потребуют раскрутки без
  `backtrace()` из обработчика, например через libunwind.

Сжатая сводка — [summary.json](summary.json).
