# Диагностика первого нагрузочного gate

Источник — сохранённый `stage8-final-gate-v1/load` на dev-ubuntu. Новые модели, симуляции, тесты и запросы сервисов при этой диагностике не запускались; исходные файлы не изменялись. [Числа, временные отметки и SHA](evidence.json).

- GRU 0/1: на 7567 мс потеря видимости у NPC 3. Все 64 команды приняты, fallback и отклонений нет. Видимость теряется во время правого обхода: направление тела и BIP расходятся примерно на 78°, лучи свободны, цель внутри радиуса. Позже удар прерывает обход и приводит к срабатыванию существующего guard. Удар не был началом потери видимости.
- GRU 2: другая причина — команда по seq 92 поступает уже после следующего периодического наблюдения. Native честно возвращает `stale_observation`, затем runtime освобождает управление. Это не основание ослаблять проверку свежести.
- Четыре native-прогона выдержали 20 секунд с четырьмя реальными NPC. Однако задержки всех четырёх сервисов превышают порог 10%; этот gate не пройден.
- Baseline отправляет 20 измеряемых запросов непрерывно, нагрузочный прогон — четырьмя сериями с паузами около 21 секунды. Первые запросы следующих серий заметно медленнее. Это наблюдаемое различие методики; оно не доказывает, что вся деградация объясняется паузами.
- Обычный RPC-ответ занимает около 45 КБ, полный статус — около 105 КБ. Native выполняет около 3587 циклов опроса за 20 секунд; четыре владельца добавляют четыре heartbeat RPC на цикл. Компактный транспорт может убрать эту лишнюю работу без изменения контрактов.

Запросы сервисов в GRU 0/1 успели завершиться за 3–5 секунд, но их нельзя зачесть: физическое владение не сохранилось на всё заявленное окно. GRU 2 сохраняет отменённые частичные запросы без зачёта. Fresh screening на момент диагностики не запускался.
